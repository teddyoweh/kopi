# KP-32 — Search insights on the backend

**Built**
- **`kopi/insights.py`**
  - `insights(store, bands, doc_nos, profile, query)`: eligibility (rules) and the snippet
    for every known tender first, then the market bands from `bands`. Unknown document
    numbers are skipped (`NotFound`), repeats are dropped, and the request's order is kept.
  - `MarketBands(store, workers=8, size=2048, ttl=300, wait=2)`: one store's bands by
    document number.
    - Lookups run on a shared 8-worker pool.
    - The cache is a bounded LRU with a five-minute TTL (the live store's notice refresh).
      It holds each lookup's future, so a lookup already in flight is shared, not repeated.
    - A batch waits at most 2 s. A band that isn't ready by then is `market=None` on that
      card, and it still fills the cache for the next call.
    - A lookup that raised is not kept, so it is retried on the next call. One tender's
      failure never fails the batch.
- **Store protocol** (`kopi/store.py`) gains `notice(doc_no)` and `market_for(notice)`:
  - `notice` is the old private `_notice`, made public in both stores.
  - `FixtureStore.market_for` is the title word-overlap that `tender()` already used.
  - `LiveStore.market_for` (`kopi/api/live.py`) starts from the notice's own stored vector
    (`Index("notices").get(doc_no)`), which is the vector search ranks it by. Only a notice
    the index doesn't hold yet is embedded, from `notice_text`, the same text ingest embeds.
  - `SIMILAR_AWARDS = 25` names the depth that was a literal in three places.
- **`LiveStore.tender()` and `overview()` now take their market from `market_for`** (see
  decision 1). This is the one change that isn't additive.
- `app.py` builds one `MarketBands` per app (`app.state.bands`) and the route passes it in.
  `POST /search/insights`, `TenderInsight` and `openapi.json` are unchanged.
- `tests/test_insights.py` has 15 tests:
  - snippet choice and fallback;
  - the 240-character clip;
  - blocker and open question;
  - skipping and order;
  - a failing lookup;
  - a 25-tender batch running in parallel;
  - the cache: across profiles, TTL, LRU, retry after failure, a slow lookup left behind
    and then reused;
  - the stored vector against the embedding fallback;
  - the card's band equals the detail page's.

  Each cache and parallelism test was checked to fail when its behaviour is removed
  (serial pool, no cache, failures cached). The suite is 300 passed.

notice bundle in `data/`, measured from this Mac to Modal)

| | 25 tenders |
|---|---|
| Before: serial, embedder on MPS (steady state) | 3.2 s |
| Before: serial, embedder on CPU at 4 threads (as deployed) | 11.5 to 11.9 s |
| After, cold cache (6 runs) | 0.8 to 1.2 s, every card with a band |
| After, warm cache, another profile | 3 ms |

- Component costs from this Mac:
  - one awards query: about 86 ms;
  - one `get` of a notice vector: 70 to 90 ms;
  - one MPS embed: 35 ms;
  - one CPU embed: 245 ms at 5 threads, 590 ms at 2.
- The first serial MPS run took 25.7 s. I put that down to MPS compiling kernels for new
  input lengths and did not prove it, so it is not the "before" figure.
- Inside Modal the round trips are shorter, so the cold figure there should be lower. It
  can only be measured after the KP-36 deploy.

**Decisions and why**
1. **One market source for the card, the detail page and the overview.** The stored vector
   is `notice_text`: title twice, agency, category, description and items. `tender()`
   embedded only `title / agency / description`.
   - On the 25 live tenders, none of the bands came out identical, and 12 of 25 medians
     moved by more than 25% (IRA000ETT26000003: $280k against $1.8M).
   - The stored vector's neighbours are the relevant ones:
     - software licensing tender: software-licence awards, against transcription,
       liquidator and insurance awards;
     - hackathon tender: "SUPPLY OF HACKATHON AND RELATED SERVICES", against geotechnical
       consultancy.
   - KP-33's preview pane shows the detail page's market right beside the card's band
     chip, so the two must agree. Moving the detail page to the stored vector is also what
     keeps it fast in production: it no longer embeds on CPU (about 250 to 600 ms per view
     deployed). On this Mac with MPS it is about 70 ms slower, because the extra round trip
     costs more than a 35 ms MPS embed.
2. **A per-tender `get` plus query on the pool, not one batched `fetch`.**
   - From this Mac, a batched fetch followed by parallel queries measured about 550 ms,
     against about 850 ms for per-tender lookups on the pool.
   - The batched version needs a batch-shaped Store method and cache. Inside Modal the
     round trips are shorter, so the gap shrinks.
   - If cold latency ever matters: `Store.markets(notices)` with one
     `Index("notices").fetch(ids)`.
3. **A deadline, not just parallelism.** While probing, about one parallel batch in 20 had
   a request hang until the NeedleDB client's 20 s timeout, which is then retried. Without
   `wait`, every card's eligibility chip would wait on it too.
4. **Cache futures, not values.** In-flight lookups are shared, stragglers fill the cache,
   and a failed future is replaced on the next lookup. No sentinels are needed.
5. **The cache is per app, not a module global.** A band only means something for one store,
   so the tests can't leak bands between stores.
6. **Eligibility isn't overlapped with the bands.** It takes about 1 ms per tender once the
   registers are cached (per UEN, per day), so overlapping would only add a two-phase API.

**Where the agent went wrong**
- I was going to take the brief literally: the stored vector for the cards, and
  `tender()` left alone. Only the side-by-side comparison showed that would put two
  different prices for the same tender on one screen. I caught it before writing code.
  - The fix was one `market_for` for all three callers.
  - A test now pins the card's band to the detail page's.
  - The lead needs to accept the non-additive change to `tender()` and `overview()`.
- My first summary test used `kind="bizsafe"`, which isn't an `EligibilityCheck` kind
  (bizSAFE checks are `licence`), so it failed at construction. It now uses `bca`.
- The slow-lookup test first waited 50 ms for the fast tender, which would flake on a
  loaded CI box. It now waits 0.5 s and asserts that the batch returned in under 2 s,
  well short of the held lookup's 5 s.
- Lint on the touched files found an extra blank line after the imports in `store.py`,
  and a `noqa` the linter didn't need. Both are fixed.
