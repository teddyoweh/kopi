# KP-12 — Modal Sandbox sessions and streaming chat

**Built**
- **`kopi/sandbox.py`, `Copilot`:** one Modal Sandbox per chat session and one
  `kopi.agent.runner` process per turn.
  - The runner's stdout (one ChatEvent per line) becomes the SSE stream.
  - Events are relabelled with Kopi's own session id. Claude's session id is kept
    server-side for `--resume`.
  - After each turn, drafts are copied out of the sandbox into the session store, so
    they download after the sandbox is gone.
  - Caps: 20 turns per session, 12 sessions per caller per day (429 when hit).
  - A dead sandbox is replaced, and the new one isn't resumed, since there's no
    transcript in it.
- **Modal adapters:**
  - `ModalBoxes` / `ModalBox`: `Sandbox.create` with `sleep infinity`, a 15-minute idle
    timeout, 1 CPU / 2 GB, the `kopi-claude` secret, and an **egress allowlist of
    api.anthropic.com, claude.ai and the Kopi API**.
  - `ModalDictStore`: a Modal Dict named `kopi-sessions` holding session records and
    drafts, shared by every API container.
- **Token scopes:**
  - A sandbox turn gets a 20-minute `scope="agent"` token (`mint_agent_token`).
  - `/chat`, `/sessions/*` and `/tenders/{doc}/overview` now require `scope="app"`
    (`AppOnly`), so the agent's token reads data but can't chat, read drafts or spend
    Claude.
- **API:** `LiveStore.chat` pulls the blocking sandbox stream on a worker thread.
  - A copilot that isn't configured answers 503.
  - A sandbox that can't start answers 503 with the reason.
  - A cap answers 429.
- **`modal_app.py`:**
  - `agent_image` has only httpx, pydantic, claude-agent-sdk and Kopi's package; no
    torch, no keys.
  - `agent_image_ready` exists so `modal deploy` builds that image ahead of the first
    chat.
  - `api()` builds the Copilot.
- **Tests:** 16 new (194 total), with a scripted fake sandbox plus API-level tests for
  SSE, scopes, 503 and 429.

**Proven live, 29 Sep 2026** (workspace kryptonairc-lc)
- The sandbox starts in **0.7 s**, from the deployed agent image.
- **Egress from inside the sandbox:**

  | Destination | Result |
  |---|---|
  | Kopi API `/health` | 200 |
  | api.anthropic.com | reachable (401 without a key) |
  | example.com | **blocked** |
  | github.com | **blocked** |
  | www.gebiz.gov.sg | **blocked** |

- The runner starts inside the sandbox, and its bundled Claude Code binary runs.
  Without a token it reports "Not logged in".
- Through the real `Copilot` path, one turn gives exactly `error`, `done` in 3.5 s, and
  the sandbox is then terminated.
- The deployed `/chat` answers **503: "could not start a copilot sandbox: Secret
  'kopi-claude' not found…"** with the link to create it.

**Not yet proven: a full Claude turn in the sandbox.** It needs the `kopi-claude`
secret (`CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token`), which only Teddy can
create. The same runner produced a full turn locally (KP-11: $0.18, a 14-question
draft). With the secret in place, one `curl` to `/chat` finishes this; see the milestone
check.

**Where the agent went wrong**
- **Chunks, not lines.** I assumed Modal's `process.stdout` yields lines, and the fake
  sandbox in the tests did. On the first live run one chunk carried two JSON events;
  the line parser would have silently dropped every second event. Only the real
  sandbox showed it. Fixed with `lines()`, which buffers and splits on newlines, plus
  tests with chunked output.
- **Duplicate error and done.** When the Claude Code binary fails (not logged in), the
  SDK first returns an error `ResultMessage`, which gives error then done, and *then*
  raises, and my exception handler emitted error then done again. Fixed: once `done`
  has gone out, an exception after it is swallowed. Regression test added.
- **A missing dev dependency.** `claude-agent-sdk` was only in the `agent` extra, so a
  clean dev install couldn't even collect `test_agent.py`. KP-11's tests passed only
  because my venv happened to have the extra. It's in the dev group now, like needledb.
- **Blamed the wrong container, again.** The first 503 carried the old message, because
  the previous deploy's container was still draining (the same trap as in KP-8). I
  retried until the new container answered instead of debugging the wrong code.
